# CFML Language Reference - database manipulation tags.
# Format: see the docstring at the top of tools/mkdocs.py.

@tag CFQUERY
category: Database manipulation
summary: Passes SQL statements to a data source and returns the result set as a query.
desc:
`CFQUERY` sends the SQL between its start and end tags to a data source. A SELECT statement
returns a query object you can loop over with `CFOUTPUT` or `CFLOOP`; INSERT, UPDATE, DELETE and
CREATE TABLE statements simply run. CFML expressions inside the tag body are evaluated before the
SQL is sent, so you can build statements from form fields and variables.
syntax:
<CFQUERY NAME="query_name"
    DATASOURCE="ds_name"
    DBTYPE="ODBC"
    MAXROWS="number"
    CACHEDWITHIN="timespan"
    CACHEDAFTER="date">
  SQL statements
</CFQUERY>
attrs:
NAME | Optional | Name of the query variable that receives the result set. Must begin with a letter and contain only
  letters, digits and underscores. Required if you want to read the results.
DATASOURCE | Required | Name of a data source registered in the KoldFusion Administrator, for example `cfsnippets`.
DBTYPE | Optional, default "ODBC" | Driver type: ODBC, OLEDB, Oracle73, Oracle80, Sybase11, Informix73 or DB2. All of them reach
  the same built-in engine in KoldFusion. DBTYPE="query" (query of queries) arrived in a later version and is rejected.
MAXROWS | Optional | Maximum number of rows to keep in the result set.
CACHEDWITHIN | Optional | A time span created with `CreateTimeSpan`. If an identical query (same name, data source and SQL)
  ran within that span, the cached result is returned without contacting the database.
CACHEDAFTER | Optional | A date. A cached result is reused if it was created after this date.
usage:
After the query runs, each result set exposes the variables `query_name.RecordCount`,
`query_name.ColumnList` and `query_name.CurrentRow`. The variable `CFQUERY.ExecutionTime` holds the
number of milliseconds the last query took.

Text values in WHERE clauses need single quotes; single quotes inside CFML variables are doubled
automatically. Use `CFQUERYPARAM` to bind typed values safely.

The maximum number of cached queries is set on the Caching page of the Administrator.

A CFQUERY can also call a stored procedure (`EXEC GetEmployeesByDept 'Sales'` or
`{call GetEmployeesByDept('Sales')}`), which returns the procedure's first result set, or run a small batch with
variables (`DECLARE @n INT; SELECT @n = MAX(Emp_ID) FROM Employees; SELECT ... WHERE Emp_ID = @n`). Use
`CFSTOREDPROC` to get output parameters, status codes and every result set.
example:
<!--- List the engineers, newest first --->
<CFQUERY NAME="GetEngineers" DATASOURCE="cfsnippets">
SELECT FirstName, LastName, StartDate
FROM Employees
WHERE Department = 'Engineering'
ORDER BY StartDate DESC
</CFQUERY>

<H3>Engineering department</H3>
<CFOUTPUT>
<P>The query returned #GetEngineers.RecordCount# rows
in #CFQUERY.ExecutionTime# ms. Columns: #GetEngineers.ColumnList#</P>
</CFOUTPUT>
<UL>
<CFOUTPUT QUERY="GetEngineers">
  <LI>#FirstName# #LastName#, since #DateFormat(StartDate, "mmmm d, yyyy")#
</CFOUTPUT>
</UL>
see: CFQUERYPARAM, CFOUTPUT, CFTRANSACTION, CFINSERT, CFUPDATE, CFSTOREDPROC, CreateTimeSpan

@tag CFQUERYPARAM
category: Database manipulation
new45: yes
summary: Binds a typed, validated value into the SQL of a CFQUERY.
desc:
`CFQUERYPARAM` goes inside a `CFQUERY` wherever a value would appear in the SQL. It checks the value
against the SQL type you name and only then hands it to the driver, so a stray quote or a sneaky
"; DELETE FROM Employees" never becomes part of the statement.
syntax:
<CFQUERYPARAM VALUE="parameter_value"
    CFSQLTYPE="parameter_type"
    MAXLENGTH="maximum_length"
    SCALE="decimal_places"
    NULL="Yes/No">
attrs:
VALUE | Required | The value to bind. Usually an expression such as `#Form.Emp_ID#`.
CFSQLTYPE | Optional, default "CF_SQL_CHAR" | The SQL type of the value: CF_SQL_BIGINT, CF_SQL_BIT, CF_SQL_CHAR,
  CF_SQL_DATE, CF_SQL_DECIMAL, CF_SQL_DOUBLE, CF_SQL_FLOAT, CF_SQL_IDSTAMP, CF_SQL_INTEGER, CF_SQL_LONGVARCHAR,
  CF_SQL_MONEY, CF_SQL_MONEY4, CF_SQL_NUMERIC, CF_SQL_REAL, CF_SQL_SMALLINT, CF_SQL_TIME, CF_SQL_TIMESTAMP,
  CF_SQL_TINYINT or CF_SQL_VARCHAR.
MAXLENGTH | Optional | Maximum length of a string value. A longer value throws a Database exception instead of
  being truncated.
SCALE | Optional | Number of decimal places for CF_SQL_DECIMAL and CF_SQL_NUMERIC; the value is rounded to it
  before it is sent.
NULL | Optional, default "No" | Yes sends SQL NULL and ignores VALUE.
LIST | Optional, default "No" | KoldFusion extension: Yes treats VALUE as a list and binds every element, for use
  inside an IN ( ) clause. Each element is validated separately.
SEPARATOR | Optional, default "," | KoldFusion extension: the list delimiter used when LIST="Yes".
usage:
Values are checked before anything reaches the data source:

- Integer types (CF_SQL_INTEGER, CF_SQL_SMALLINT, CF_SQL_TINYINT, CF_SQL_BIGINT) accept whole numbers only.
- The other numeric types (DECIMAL, NUMERIC, FLOAT, DOUBLE, REAL, MONEY) accept any number.
- CF_SQL_BIT accepts Yes/No, True/False or a number and sends 1 or 0.
- CF_SQL_DATE, CF_SQL_TIME and CF_SQL_TIMESTAMP accept anything `IsDate` likes and send an ODBC date literal.
- Everything else is treated as text; single quotes are doubled for you.

A value that fails the check throws an exception of type Database ("Invalid data ... for CFSQLTYPE ..."),
which you can catch with `CFTRY`/`CFCATCH`. Using the tag outside a `CFQUERY` is a Template error.
example:
<!--- Try ?Dept=Marketing&MinID=7 or ?MinID=abc --->
<CFPARAM NAME="URL.Dept" DEFAULT="Engineering">
<CFPARAM NAME="URL.MinID" DEFAULT="10">
<CFTRY>
  <CFQUERY NAME="GetStaff" DATASOURCE="cfsnippets">
  SELECT Emp_ID, FirstName, LastName
  FROM Employees
  WHERE Department = <CFQUERYPARAM VALUE="#URL.Dept#" CFSQLTYPE="CF_SQL_VARCHAR" MAXLENGTH="35">
    AND Emp_ID >= <CFQUERYPARAM VALUE="#URL.MinID#" CFSQLTYPE="CF_SQL_INTEGER">
  ORDER BY Emp_ID
  </CFQUERY>
  <CFOUTPUT><H3>#HTMLEditFormat(URL.Dept)#, employee ID #HTMLEditFormat(URL.MinID)# and up</H3></CFOUTPUT>
  <TABLE BORDER=1 CELLPADDING=3>
  <TR><TH>ID</TH><TH>Name</TH></TR>
  <CFOUTPUT QUERY="GetStaff">
  <TR><TD>#Emp_ID#</TD><TD>#FirstName# #LastName#</TD></TR>
  </CFOUTPUT>
  </TABLE>
  <CFCATCH TYPE="Database">
    <CFOUTPUT><P><B>Rejected:</B> #CFCATCH.Message#</P></CFOUTPUT>
  </CFCATCH>
</CFTRY>

<!--- A hostile value never reaches the database --->
<CFTRY>
  <CFQUERY NAME="Sneaky" DATASOURCE="cfsnippets">
  SELECT * FROM Employees
  WHERE Emp_ID = <CFQUERYPARAM VALUE="3; DELETE FROM Employees" CFSQLTYPE="CF_SQL_INTEGER">
  </CFQUERY>
  <CFCATCH TYPE="Database">
    <CFOUTPUT><P><B>Also rejected:</B> #CFCATCH.Message#</P></CFOUTPUT>
  </CFCATCH>
</CFTRY>
see: CFQUERY, CFPROCPARAM, CFTRY, IsNumeric

@tag CFTRANSACTION
category: Database manipulation
summary: Groups several CFQUERY operations into a single database transaction.
desc:
Put `CFQUERY` tags between `<CFTRANSACTION>` and `</CFTRANSACTION>` when they belong together, such as
debiting one account and crediting another. On a transactional driver the group is committed when the end
tag is reached, or rolled back if an error occurs inside it.
syntax:
<CFTRANSACTION ACTION="BEGIN"
    ISOLATION="lock_level">
  CFQUERY tags
</CFTRANSACTION>
attrs:
ACTION | Optional, default "BEGIN" | BEGIN, COMMIT or ROLLBACK. COMMIT and ROLLBACK are used in a nested
  CFTRANSACTION to end the current transaction early (ROLLBACK undoes everything written so far).
ISOLATION | Optional | ODBC lock level: READ_UNCOMMITTED, READ_COMMITTED, REPEATABLE_READ or SERIALIZABLE. Any other
  value is an error. The flat-file driver always behaves as SERIALIZABLE, since every statement runs alone.
usage:
> The built-in flat-file driver has no transaction log, so KoldFusion snapshots the tables of each data
> source the first time a statement writes to it inside the transaction. If an error escapes the
> `CFTRANSACTION` block, or a nested `<CFTRANSACTION ACTION="ROLLBACK">` runs, the snapshot is restored;
> otherwise the changes are kept when the end tag is reached. Other requests can see uncommitted changes
> (there is no isolation), so keep transactions short.

All queries inside one transaction must use the same data source. To keep two users from interleaving
updates to shared variables (not tables), use `CFLOCK`.
example:
<!--- Add a comment, look at it, take it back out again --->
<CFQUERY NAME="Before" DATASOURCE="cfsnippets">
SELECT COUNT(*) AS Total FROM Comments
</CFQUERY>

<CFTRANSACTION>
  <CFQUERY DATASOURCE="cfsnippets">
  INSERT INTO Comments (Email, FromUser, Subject, CommtType, MessText, Processed)
  VALUES ('ann@localhost', 'Ann Example', 'Transaction test', 'Question', 'Testing 1, 2, 3', 0)
  </CFQUERY>
  <CFQUERY NAME="During" DATASOURCE="cfsnippets">
  SELECT COUNT(*) AS Total, MAX(CommentID) AS LastID FROM Comments
  </CFQUERY>
  <CFQUERY DATASOURCE="cfsnippets">
  DELETE FROM Comments WHERE CommentID = #During.LastID#
  </CFQUERY>
</CFTRANSACTION>

<CFQUERY NAME="After" DATASOURCE="cfsnippets">
SELECT COUNT(*) AS Total FROM Comments
</CFQUERY>

<CFOUTPUT>
<TABLE BORDER=1 CELLPADDING=3>
<TR><TH>Moment</TH><TH>Rows in Comments</TH></TR>
<TR><TD>Before the transaction</TD><TD>#Before.Total#</TD></TR>
<TR><TD>After the INSERT (new ID #During.LastID#)</TD><TD>#During.Total#</TD></TR>
<TR><TD>After the DELETE</TD><TD>#After.Total#</TD></TR>
</TABLE>
</CFOUTPUT>
see: CFQUERY, CFLOCK, CFTRY, CFUPDATE

@tag CFINSERT
category: Database manipulation
summary: Inserts the fields of a submitted form as a new row of a table, without writing any SQL.
desc:
`CFINSERT` is the lazy programmer's INSERT statement. It looks at the columns of the table, finds the form
fields with the same names, and adds one row built from their values.
syntax:
<CFINSERT DATASOURCE="ds_name"
    TABLENAME="table_name"
    TABLEOWNER="owner"
    TABLEQUALIFIER="qualifier"
    USERNAME="username"
    PASSWORD="password"
    FORMFIELDS="field_names">
attrs:
DATASOURCE | Required | Data source that holds the table.
TABLENAME | Required | Table to insert into.
FORMFIELDS | Optional, default all fields | Comma-separated list of form fields to insert. Without it, every
  name in `Form.FieldNames` that matches a column is used.
TABLEOWNER | Optional | Owner of the table on servers that support owners. Accepted for compatibility;
  KoldFusion ignores it.
TABLEQUALIFIER | Optional | Database or schema qualifier. Accepted for compatibility; KoldFusion ignores it.
USERNAME | Optional | Overrides the user name stored with the data source. Accepted for compatibility;
  KoldFusion ignores it.
PASSWORD | Optional | Overrides the password stored with the data source. Accepted for compatibility;
  KoldFusion ignores it.
usage:
Field names are matched to column names without regard to case. Fields with no matching column (such as the
Submit button) are skipped, and so are COUNTER (autonumber) columns, which the database fills in. An empty
field bound for a numeric column is stored as NULL. If not a single field matches a column, a Database
exception is thrown.

To find the key of the row you just added, run `SELECT MAX(id_column)` (or `SELECT @@IDENTITY`) in a
`CFQUERY` straight afterwards. For full control over the SQL, use `CFQUERY` with `CFQUERYPARAM`.
example:
<CFIF IsDefined("Form.FromUser")>
  <CFINSERT DATASOURCE="cfsnippets" TABLENAME="Comments"
            FORMFIELDS="FromUser,Email,Subject,CommtType,MessText">
  <CFQUERY NAME="Newest" DATASOURCE="cfsnippets">
  SELECT MAX(CommentID) AS LastID FROM Comments
  </CFQUERY>
  <CFQUERY NAME="Added" DATASOURCE="cfsnippets">
  SELECT * FROM Comments WHERE CommentID = #Newest.LastID#
  </CFQUERY>
  <CFOUTPUT QUERY="Added">
  <P>Thank you! Comment ###CommentID# was stored:</P>
  <TABLE BORDER=1 CELLPADDING=3>
  <TR><TD>From</TD><TD>#HTMLEditFormat(FromUser)# (#HTMLEditFormat(Email)#)</TD></TR>
  <TR><TD>Subject</TD><TD>#HTMLEditFormat(Subject)# [#CommtType#]</TD></TR>
  <TR><TD>Message</TD><TD>#HTMLEditFormat(MessText)#</TD></TR>
  </TABLE>
  </CFOUTPUT>
  <!--- Tidy up, so the next visitor finds the table as it was --->
  <CFQUERY DATASOURCE="cfsnippets">
  DELETE FROM Comments WHERE CommentID = #Newest.LastID#
  </CFQUERY>
  <P>(The row has been removed again.) <A HREF="cfinsert.cfm">Try again</A></P>
<CFELSE>
  <FORM ACTION="cfinsert.cfm" METHOD="POST">
  Name: <INPUT TYPE="Text" NAME="FromUser" VALUE="Pat Kowal"><BR>
  Email: <INPUT TYPE="Text" NAME="Email" VALUE="pat@localhost"><BR>
  Subject: <INPUT TYPE="Text" NAME="Subject" VALUE="Nice site"><BR>
  Type: <SELECT NAME="CommtType"><OPTION>Praise<OPTION>Question<OPTION>Bug Report</SELECT><BR>
  <TEXTAREA NAME="MessText" ROWS=3 COLS=40>Loads fast even on my 56K modem.</TEXTAREA><BR>
  <INPUT TYPE="Submit" VALUE="Insert comment">
  </FORM>
</CFIF>
see: CFUPDATE, CFQUERY, CFQUERYPARAM, CFFORM

@tag CFUPDATE
category: Database manipulation
summary: Updates an existing table row from the fields of a submitted form, without writing any SQL.
desc:
`CFUPDATE` is the companion of `CFINSERT`. The form must contain a field named after the table's primary
key; that field picks the row, and the other fields whose names match columns supply the new values.
syntax:
<CFUPDATE DATASOURCE="ds_name"
    TABLENAME="table_name"
    TABLEOWNER="owner"
    TABLEQUALIFIER="qualifier"
    USERNAME="username"
    PASSWORD="password"
    FORMFIELDS="field_names">
attrs:
DATASOURCE | Required | Data source that holds the table.
TABLENAME | Required | Table to update.
FORMFIELDS | Optional, default all fields | Comma-separated list of form fields to use. Include the primary key
  field. Without it, every name in `Form.FieldNames` that matches a column is used.
TABLEOWNER | Optional | Accepted for compatibility; KoldFusion ignores it.
TABLEQUALIFIER | Optional | Accepted for compatibility; KoldFusion ignores it.
USERNAME | Optional | Accepted for compatibility; KoldFusion ignores it.
PASSWORD | Optional | Accepted for compatibility; KoldFusion ignores it.
usage:
The KoldFusion flat-file driver keeps no catalog of keys, so the **first column** of the table is taken to be
the primary key (CommentID for Comments, Emp_ID for Employees). If the form has no field with that name, a
Database exception is thrown. Columns that are not in the form keep their old values; if no other field
matches a column, nothing happens at all.

A common pattern is an edit form that carries the key in a hidden field:
`<INPUT TYPE="Hidden" NAME="Emp_ID" VALUE="#Emp_ID#">`.
example:
<!--- Edits comment 3, then puts it back the way it was --->
<CFQUERY NAME="Original" DATASOURCE="cfsnippets">
SELECT CommentID, Subject FROM Comments WHERE CommentID = 3
</CFQUERY>
<CFIF IsDefined("Form.CommentID")>
  <CFUPDATE DATASOURCE="cfsnippets" TABLENAME="Comments" FORMFIELDS="CommentID,Subject">
  <CFQUERY NAME="Changed" DATASOURCE="cfsnippets">
  SELECT Subject FROM Comments WHERE CommentID = 3
  </CFQUERY>
  <CFOUTPUT>
  <TABLE BORDER=1 CELLPADDING=3>
  <TR><TD>Subject before</TD><TD>#HTMLEditFormat(Original.Subject)#</TD></TR>
  <TR><TD>Subject after CFUPDATE</TD><TD>#HTMLEditFormat(Changed.Subject)#</TD></TR>
  </TABLE>
  </CFOUTPUT>
  <!--- Restore the original subject for the next visitor --->
  <CFQUERY DATASOURCE="cfsnippets">
  UPDATE Comments
  SET Subject = <CFQUERYPARAM VALUE="#Original.Subject#" CFSQLTYPE="CF_SQL_VARCHAR">
  WHERE CommentID = 3
  </CFQUERY>
  <P>(The original subject has been restored.) <A HREF="cfupdate.cfm">Try again</A></P>
<CFELSE>
  <CFOUTPUT>
  <FORM ACTION="cfupdate.cfm" METHOD="POST">
  <INPUT TYPE="Hidden" NAME="CommentID" VALUE="#Original.CommentID#">
  Subject of comment #Original.CommentID#:
  <INPUT TYPE="Text" NAME="Subject" SIZE=30 VALUE="#HTMLEditFormat(Original.Subject)# - is my PC Y2K OK?">
  <INPUT TYPE="Submit" VALUE="Update">
  </FORM>
  </CFOUTPUT>
</CFIF>
see: CFINSERT, CFQUERY, CFQUERYPARAM, CFFORM

@tag CFSTOREDPROC
category: Database manipulation
summary: Calls a stored procedure in a data source.
desc:
`CFSTOREDPROC` calls a procedure stored in the database itself. Nested `CFPROCPARAM` tags pass its
parameters and receive its output parameters; `CFPROCRESULT` tags turn the result sets it returns into
ordinary query variables. Like an ODBC driver, KoldFusion sends the call as `{? = call Name(?, ?)}` and binds the
parameters by position, or by name when `CFPROCPARAM` has a DBVARNAME.

The KoldFusion Flat-File Driver keeps each procedure as a text file next to the tables of its data source.
Create one with a `CREATE PROCEDURE` statement in a `CFQUERY` (see Usage); the cfsnippets data source comes
with GetEmployeesByDept, AddEmployee, CountByDept and GetEmployee.
syntax:
<CFSTOREDPROC PROCEDURE="procedure_name"
    DATASOURCE="ds_name"
    USERNAME="username"
    PASSWORD="password"
    DBSERVER="dbms"
    DBNAME="database_name"
    BLOCKFACTOR="blocksize"
    PROVIDER="COMProvider"
    PROVIDERDSN="datasource"
    DEBUG="Yes/No"
    RETURNCODE="Yes/No">
  CFPROCPARAM and CFPROCRESULT tags
</CFSTOREDPROC>
attrs:
PROCEDURE | Required | Name of the stored procedure. An owner prefix such as `dbo.AddEmployee` is accepted.
DATASOURCE | Required | Data source that holds the procedure.
USERNAME | Optional | Overrides the login name in the data source definition. The flat-file driver does not check it.
PASSWORD | Optional | Overrides the password in the data source definition. The flat-file driver does not check it.
DBSERVER | Optional | Server name for native drivers. Ignored by the flat-file driver.
DBNAME | Optional | Database name for native drivers. Ignored by the flat-file driver.
BLOCKFACTOR | Optional, default "1" | Rows fetched from the server at a time, 1 to 100. Other values are rejected.
PROVIDER | Optional | COM provider for OLE DB data sources.
PROVIDERDSN | Optional | Data source name for the COM provider (OLE DB only).
DEBUG | Optional, default "No" | Yes lists the call, every parameter and the number of result sets in the
  debugging output, even when "Show query information" is off in the Administrator.
RETURNCODE | Optional, default "No" | Yes puts the procedure's status code, the value of its RETURN statement, in
  `CFSTOREDPROC.StatusCode`.
usage:
After the call, `CFSTOREDPROC.ExecutionTime` holds the time the procedure took, in milliseconds, and with
RETURNCODE="Yes" `CFSTOREDPROC.StatusCode` holds its status code (0 when the procedure has no RETURN).
Errors raised by the procedure arrive as Database exceptions with the usual ODBC SQLState, for example 37000
for an unknown procedure and 07001 for a missing or extra parameter.

# Writing procedures

The flat-file driver speaks the procedure dialect of SQL Server and Sybase. A procedure declares its
parameters with an `@`, a type, an optional default and OUTPUT for output parameters:

    CREATE PROCEDURE RaiseSalary
        @EmpID   INT,
        @Percent NUMERIC(5,2) = 5,
        @Salary  MONEY OUTPUT
    AS
    BEGIN
        IF NOT EXISTS (SELECT * FROM Employees WHERE Emp_ID = @EmpID)
            RETURN 1;
        UPDATE Employees SET Salary = Salary * (100 + @Percent) / 100 WHERE Emp_ID = @EmpID;
        SELECT @Salary = Salary FROM Employees WHERE Emp_ID = @EmpID;
        RETURN 0;
    END

The body can use any SQL the driver understands, with `@variables` wherever a value may appear, plus:

| Statement | What it does |
| DECLARE @v type [, ...] | Declares local variables (initially NULL). |
| SET @v = expression | Assigns a value; the expression may be a subquery: `SET @n = (SELECT COUNT(*) FROM Parks)`. |
| SELECT @v = column, ... FROM ... | Assigns from a query (the last row wins; no rows leaves the variables alone). |
| SELECT ... | Any other SELECT returns a result set to the caller. |
| IF condition statement [ELSE statement] | Conditions may use EXISTS, IN, subqueries and IS NULL. |
| WHILE condition statement | Loops, with BREAK and CONTINUE. |
| BEGIN ... END | Groups statements. |
| RETURN [n] | Ends the procedure with status code n (default 0). |
| EXEC proc args | Calls another procedure: positional, `@name = value`, DEFAULT and `@v OUTPUT` arguments, `EXEC @rc = proc`. |
| RAISERROR ('text %s', 16, 1, args) | Fails with your own message; severity 10 or less is ignored. |
| PRINT, SET NOCOUNT ON, BEGIN TRAN, COMMIT | Accepted and ignored (use `CFTRANSACTION` for transactions). |

`@@ROWCOUNT`, `@@IDENTITY` and `@@NESTLEVEL` work as in SQL Server. Separate statements with semicolons or
start each one on a statement keyword. Remove a procedure with `DROP PROCEDURE name`; change one with
`ALTER PROCEDURE`.

In a CFQUERY you can also call a procedure with `EXEC name args`, `{call name(args)}` or `CALL name(args)`; the
query receives the procedure's first result set. A CFQUERY may also hold a whole batch that uses variables,
for example `DECLARE @n INT; SET @n = 5; SELECT TOP @n ...`.

> Procedures, like the tables, live in the data source's directory under `kfroot/db/`, one `.prc` file each. The
> Administrator's table browser (Data Sources > ODBC > View Tables) lists them with their parameters and source.
example:
<!--- Department head counts: two result sets, an output parameter and a status code --->
<CFSTOREDPROC PROCEDURE="CountByDept" DATASOURCE="cfsnippets" RETURNCODE="Yes">
  <CFPROCPARAM TYPE="In" CFSQLTYPE="CF_SQL_VARCHAR" DBVARNAME="@Department" NULL="Yes">
  <CFPROCPARAM TYPE="Out" CFSQLTYPE="CF_SQL_INTEGER" DBVARNAME="@Total" VARIABLE="TotalStaff">
  <CFPROCRESULT NAME="HeadCount" RESULTSET="1">
  <CFPROCRESULT NAME="Offices" RESULTSET="2">
</CFSTOREDPROC>

<CFOUTPUT>
<P>CountByDept returned status #CFSTOREDPROC.StatusCode# in #CFSTOREDPROC.ExecutionTime# ms:
#TotalStaff# employees in #HeadCount.RecordCount# departments.</P>
</CFOUTPUT>
<TABLE BORDER=1 CELLPADDING=3>
<TR BGCOLOR="#CCCCCC"><TH>Department</TH><TH>Employees</TH><TH>Payroll</TH></TR>
<CFOUTPUT QUERY="HeadCount">
<TR><TD>#Department#</TD><TD ALIGN="right">#Employees#</TD><TD ALIGN="right">#DollarFormat(Payroll)#</TD></TR>
</CFOUTPUT>
</TABLE>
<P>Offices:
<CFOUTPUT QUERY="Offices">#Dept_Name# (#Location#)<CFIF CurrentRow LT RecordCount>, </CFIF></CFOUTPUT></P>
see: CFPROCPARAM, CFPROCRESULT, CFQUERY, CFTRANSACTION, CFQUERYPARAM

@tag CFPROCPARAM
category: Database manipulation
summary: Passes one parameter to a stored procedure called with CFSTOREDPROC.
desc:
Each `CFPROCPARAM` inside a `CFSTOREDPROC` supplies one parameter. Without DBVARNAME the parameters are
matched to the procedure's parameters in the order the procedure declares them; with DBVARNAME they are matched
by name. Input parameters carry a value; output parameters name a CFML variable that receives the
procedure's value when the call returns.
syntax:
<CFPROCPARAM TYPE="In/Out/InOut"
    VARIABLE="variable_name"
    DBVARNAME="db_variable_name"
    VALUE="parameter_value"
    CFSQLTYPE="parameter_datatype"
    MAXLENGTH="length"
    SCALE="decimal_places"
    NULL="Yes/No">
attrs:
TYPE | Optional, default "In" | In passes a value, Out receives one, InOut does both.
VARIABLE | Required for Out and InOut | CFML variable that receives the output value. A NULL comes back as an empty
  string, a date as "yyyy-mm-dd hh:mm:ss", like the columns of a query.
DBVARNAME | Optional | Name of the parameter in the procedure, such as `@Department`, to bind by name instead of by
  position. Positional parameters must come before named ones.
VALUE | Required for In and InOut | The value to pass. It is checked against CFSQLTYPE before the call.
CFSQLTYPE | Required | CF_SQL_BIGINT, CF_SQL_BIT, CF_SQL_CHAR, CF_SQL_DATE, CF_SQL_DECIMAL, CF_SQL_DOUBLE, CF_SQL_FLOAT,
  CF_SQL_IDSTAMP, CF_SQL_INTEGER, CF_SQL_LONGVARCHAR, CF_SQL_MONEY, CF_SQL_MONEY4, CF_SQL_NUMERIC, CF_SQL_REAL,
  CF_SQL_REFCURSOR, CF_SQL_SMALLINT, CF_SQL_TIME, CF_SQL_TIMESTAMP, CF_SQL_TINYINT or CF_SQL_VARCHAR.
  CF_SQL_REFCURSOR (Oracle cursors) is refused by the flat-file driver, which returns result sets directly.
MAXLENGTH | Optional | Maximum length of an input value (longer values throw an exception) and of a returned string.
SCALE | Optional | Decimal places a returned numeric value is rounded to.
NULL | Optional, default "No" | Yes passes SQL NULL and ignores VALUE.
usage:
The procedure converts each value to the type it declares: a VARCHAR(5) parameter keeps five characters, an
INT drops the fraction, and a value that does not convert ends the call with "Conversion failed when
converting ...". Leave out a parameter that has a default, or bind it by name and skip it.

A procedure parameter must be declared OUTPUT for a TYPE="Out" or "InOut" `CFPROCPARAM`; otherwise the call
fails with "The formal parameter ... was not declared as an OUTPUT parameter".
example:
<!--- AddEmployee returns the new Emp_ID in an output parameter and a status code:
      0 = added, 1 = no such department, 2 = already on file.
      The transaction is rolled back, so the sample data stays the same. --->
<CFTRANSACTION>
  <CFSTOREDPROC PROCEDURE="AddEmployee" DATASOURCE="cfsnippets" RETURNCODE="Yes">
    <CFPROCPARAM TYPE="In" CFSQLTYPE="CF_SQL_VARCHAR" DBVARNAME="@FirstName" VALUE="Wendy">
    <CFPROCPARAM TYPE="In" CFSQLTYPE="CF_SQL_VARCHAR" DBVARNAME="@LastName" VALUE="Okonkwo">
    <CFPROCPARAM TYPE="In" CFSQLTYPE="CF_SQL_VARCHAR" DBVARNAME="@Department" VALUE="Training">

@tag CFPROCRESULT
category: Database manipulation
summary: Names a result set returned by a stored procedure called with CFSTOREDPROC.
desc:
A stored procedure returns one result set for each SELECT it runs. Each `CFPROCRESULT` inside a
`CFSTOREDPROC` turns one of them into an ordinary query variable that you can use with `CFOUTPUT`, `CFLOOP` and
the query functions.
syntax:
<CFPROCRESULT NAME="query_name"
    RESULTSET="1-n"
    MAXROWS="maxrows">
attrs:
NAME | Required | Name of the query that receives the result set.
RESULTSET | Optional, default "1" | Which result set to take, counting from 1.
MAXROWS | Optional | Maximum number of rows to keep.
usage:
Result sets are numbered in the order the procedure produces them, including those of procedures it calls with
EXEC. If the procedure returns fewer result sets than RESULTSET asks for, the query variable is not created;
test for it with `IsDefined` before you use it.
example:
<CFSTOREDPROC PROCEDURE="CountByDept" DATASOURCE="cfsnippets">
  <CFPROCPARAM TYPE="In" CFSQLTYPE="CF_SQL_VARCHAR" VALUE="Engineering">
  <CFPROCPARAM TYPE="Out" CFSQLTYPE="CF_SQL_INTEGER" VARIABLE="Total">
  <CFPROCRESULT NAME="Depts" RESULTSET="1">
  <CFPROCRESULT NAME="Offices" RESULTSET="2" MAXROWS="1">
  <CFPROCRESULT NAME="Third" RESULTSET="3">
</CFSTOREDPROC>
<CFOUTPUT>
<P>Engineering has #Total# employees and a payroll of #DollarFormat(Depts.Payroll)#.
It is based in #Offices.Location#.</P>
<P>IsDefined("Third"): #IsDefined("Third")# (CountByDept returns two result sets).</P>
</CFOUTPUT>

<!--- The same procedure's first result set, through CFQUERY --->
<CFQUERY NAME="ViaQuery" DATASOURCE="cfsnippets">
EXEC CountByDept @Department = 'Sales', @Total = NULL
</CFQUERY>
<CFOUTPUT QUERY="ViaQuery"><P>Via CFQUERY: #Department#, #Employees# employees.</P></CFOUTPUT>
see: CFSTOREDPROC, CFPROCPARAM, CFQUERY, IsDefined
